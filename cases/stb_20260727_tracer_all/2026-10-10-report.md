## 10. Why frame 256 is a copy (D3; 10 Oct)

You asked why it happens, starting from `imgFile`, which holds the raw videos minus a background image. `imgFile_mask` is
`imgFile` with the bubbles masked out, using the masks in `imgFile_bb`.

**The cause: pyOpenLPT's image preprocessing reads the videos one frame off, in chunks of 256.**
- **The videos:** `Raw_Data\20260727\<run>\CamC1.cine` … `CamC4.cine`, 63 GB each. Their headers number the frames from
  0 (`FirstImageNo` 0) and hold 12,605 frames: 10-bit packed, 2048 × 1952 pixels, 5000 fps.
- **How the GUI converts them** (`modules/image_preprocessing/view.py`, the batch worker, lines 177–206):
  - it lists each video's frames by the camera's numbering, `FirstImageNo` … `FirstImageNo + ImageCount − 1`, here
    0 … 12,604, and writes the n-th frame of the list to `img<n>.tif`;
  - it reads them in chunks of 256 with pycine's `read_frames(cine, start_frame=<first frame of the chunk>, count=…)`.
- **What pycine does with `start_frame`** (pycine 0.3.2, `pycine/raw.py`):
  - it reads the stored frame at position `start_frame − 1`. So `start_frame` counts from 1, although its docstring
    says that 0 means the first frame;
  - it takes `start_frame = 0` as "not given" (`0 == False` in Python) and makes it 1.
- **Together:**
  - the first chunk asks for 0, gets 1, and reads stored frames 0–255, so files 0–255 are right;
  - every later chunk (256, 512, …) starts one stored frame early. File 256 repeats stored frame 255, and from there
    file j holds stored frame j − 1;
  - the video's last frame (12,604) is never written. The 12,605 files hold 12,604 different frames.
- **The file times fit:** each chunk of 256 is read at once, then processed and written in parallel. So the times jump
  at every multiple of 256 and run out of order inside a chunk (D2).

**Checked against the videos** (`tests/cine_frames.py` → `cine_frames_35Hz_r_b_1.txt`, `cine_frames_10Hz_r_b_1.txt`,
each with its `.json`):
- **Headers:** `FirstImageNo` 0 and `ImageCount` 12,605 in all three videos read (35Hz_r_b_1, cameras 0 and 1;
  10Hz_r_b_1, camera 0).
- **pycine:** `start_frame=0` and `start_frame=1` return the same stored frame; 1 and 2 differ.
- **Every file checked holds the frame the chunked reading predicts.**
  - **Files checked:** 0, 1, 2, 254, 255, 256, 257, 258, 511, 512, 513, 12,603 and 12,604, each against the stored
    frames from two before to two after it.
  - **How matched:** by correlation. `imgFile` is the raw frame inverted, so the match is the most negative value.
  - **Result:** file 256 is stored frame 255, file 257 is 256 and file 12,604 is 12,603. Stored frame 12,604 is in no
    file.
- **The masks follow:** `imgFile_bb` frame 256 is a byte copy of frame 255 too (`frame256_bb.txt`), as in
  `imgFile_mask`. The three folders hold the same frame in each file, so masks and images are not offset.

**Other code with the same mistake** (it passes the camera's frame number as pycine's `start_frame`):
- **In `view.py`:**
  - the per-frame fallback of the batch (line 245);
  - the background average (chunks of 100; lines 412 and 438), which counts one frame twice per chunk and leaves out
    the last, hardly changing it;
  - the preview (`_read_image`, line 2193), which shows stored frame 0 for frames 0 and 1, and stored frame k − 1 for
    frame k.
- **In `io.py`,** used by the command-line preprocessing:
  - `read_cine_frame` reads frame by frame, so its copy is at frame 1 rather than 256;
  - `compute_mean_background_from_cine` reads in chunks of 128.
- **Worse for a video numbered from below 0** (frames recorded before the trigger): pycine takes negative positions
  from the end of the file, so the first images would come from the end of the recording.

**What it means for the results:**
- **The image folders:** all three, in every run, have the copy at 256 and are one frame late from 257 on. So has
  anything else converted from .cine by pyOpenLPT with more than 256 frames.
- **`10Hz_r_b_1`'s tracer results and `Results_bb`** use the file numbers. Frame 256 repeats frame 255, and from 257 on
  frame k is the video's frame k − 1.
- **Leaving file 256 out of the image lists** makes STB's frame k the video's frame k, for k = 0 … 12,603. Only the
  video's last frame is missing.

**Choices for you:**
- **Fix the code** (with a plan for your approval first):
  - one function that turns the camera's frame number into pycine's position (`start_frame = frame − FirstImageNo + 1`),
    used at all eight calls (seven, as first counted here);
  - a test against the stored frames of a real video;
  - new conversions would then be right for any `FirstImageNo`.
- **The images already converted:**
  - **Leave file 256 out of the image lists (recommended for the tracer runs):**
    - no files change, and frame numbers follow the video;
    - `10Hz_r_b_1` and `Results_bb` stay one frame off from 257 on, unless redone or renumbered the same way;
      `10Hz_r_b_1` could be redone from its save at frame 200 (about 13 h).
  - **Reconvert** with the fixed code and remake the bubble masks:
    - every file is right, the last frame included;
    - from the file times, it takes about 3 h per run for `imgFile` and 1.5 h for the masks, so 2–3 days for all
      twelve.
  - **Keep them as they are,** with the copy at 256, as `10Hz_r_b_1` was tracked.
