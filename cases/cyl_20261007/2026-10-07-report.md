## 1. In short

**T1 is tracked** with the new library (build p4c) on all 251 processed frames, every 4th raw frame (1 ms steps),
with T0's calibration:
- **Tracks:** 701 long ones, holding 64,011 positions. About 335 particles per frame are in long tracks once the
  tracking has built up (frames 150–250). The median track spans 76 steps; 259 tracks span at least 100 and 60 at
  least 200.
- **The flow is a swirl about the tube's axis:** arcs about the axis, at 31–105 mm/s (10–90 %, median 67), with

- **The tracks fit the images.** The tracked particles' images lie 0.26–0.78 px RMS from their detections. Their
  shapes agree with the shape model (68 % within 0.44–0.65 px). The cameras did not move after T0 (mean epipolar
  residual +0.06 ± 0.04 px), and T1 shows no time offset between them (0.38 ± 0.39 raw frames).
- **About half the long tracks may still be ghosts.** I added a control: the same run with cam2's images 0.1 s
  later, so that every match is false.
  - By frame 100 it builds half as many long tracks as the real run (ratio 0.52, an upper bound on the ghost share).
  - Its tracks are much less tangential to the swirl than the real run's.
  - Both estimates put the ghosts at 44–51 %.
- **Today's code on T1 tracks noise.** It gives about 2,450 long tracks in 61 frames, less swirl-like than the
  control's pure ghosts, and their shapes disagree with the model.

**Why not more, and why ghosts remain:**
- **Two cameras at T1's density.** There are about 1,000 line detections per camera per frame, but only about 250
  true stereo pairs per frame show up within 3 px of the epipolar curves (25 %).
- **The calibration spreads the true pairs:** T0's error pattern (0.5–1 px) spreads them over ±2 px of the curves.
- **The depth cue filters only so far:** it keeps half the true pairs and 3 % of the random ones.
- **The remaining ghosts persist:** their two detections both move with the flow, so they form coherent tracks.

### 4.2 S2, the shape model

`tests/s2_shape_fit_out.txt`, `.json`, `s2_shape_fit.png`; the gathering run's per-frame log is in
`s2_shape_fit_console.txt`. The model is in `data/T1_shape.json`, its OTF table in `data/T1_otf_shape.txt`, and
both are on X:.

**Model.** Per camera: a pupil of diameter A focused at depth z_f, and a base blur σ0. A point images as an
ellipse with full axes L = A f |1/z − 1/z_f|, along u with the tangential depth z_tan and along v with the sagittal
z_sag. Both depths come from the calibrated PINCYL camera, as the parallax of a displaced pinhole. What is compared
is the RMS widths: the detector's √(L²/12 + s²) against the model's √(L²/16 + σ0²).

**Which pairs are true.** Two cameras at T1's density make matching ambiguous:
- each cam1 detection's curved image line on cam2 passes within 1.5 px of about 3 cam2 detections;
- about 252 true pairs per frame stand out as a peak on a flat floor of random pairs (`t1a_epipolar_offset.png`);
- that is one true pair to about 16 random ones within 1.5 px.

**Why the first fits were wrong.** They maximised the number of pairs that agreed with the model, and so fitted the
random pairs. They are kept in `tests/before_s2_*`:
- `before_s2_widths/`: the length model, which collapsed to A → 0;
- `before_s2_bgsub/`: the width model fitted to all pairs, A 8.2 mm, which the Planes contradict by 2–3×.

**How this one is fitted.** It separates the true pairs statistically:
- every pair within 8 px of the curve is gathered, over 51 frames;
- the pairs within 1.5 px form the signal band and those 4–8 px away the background band, which holds only random
  pairs;
- any count or sum taken over the signal band, minus 1.5/4 times the same over the background band, estimates it
  for the true pairs;
- the model is fitted to maximise the true pairs that agree, on 26 frames, and judged on the other 25.

**Result: model A** (no depth offset; model B's offset changed nothing):

| | A (pupil) | z_f | σ0 | 68 % of true pairs' \|residual\| within (w_h / w_v) | trend over the depths (w_h / w_v) |
|---|---|---|---|---|---|
| cam1 | 20.0 mm | 1,167.1 mm | 1.20 px | 0.94 / 0.50 px | −0.88 / +0.66 px |
| cam2 | 15.25 mm | 822.3 mm | 1.23 px | 0.42 / 0.43 px | −0.65 / +0.37 px |

- **Judged (plan L3):** the residuals pass (68 % within 1.5 px), the trend with depth fails. Each camera has a
  residual slope of 0.4–0.9 px over the depth range, significant for cam1. A linear depth correction fitted on the
  true pairs would not help the depth cue (+2 % in its figure of merit), so the model is used as it is.
- **The amplitude** is empirical (the flux grows with the image's size, lines report §6): cam1
  787.5·(|b|+|c|+2)^0.468, cam2 83.9·(|b|+|c|+2)^1.165.
- **True matches are spread across the curve:** within 1.0 px of it 65 %, 1.5 px 81 %, 2.0 px 90 % (of those
  within 3 px). Its centre is at −0.19 / +0.14 px (T1-a, `t1a_epipolar_offset_out.txt`), so the cameras did not
  move after T0. The spread is T0's calibration error pattern (Phase C report §3: 0.46 / 0.96 px), and it is why
  S3 uses a 1.5 px tolerance.

**The depth cue's worth** on the held-out frames (`shape_check` on both cameras):

| tolerances (px, relative) | true pairs kept | random pairs kept |
|---|---|---|
| 0.5, 0.20 | 29 % | 1.3 % |
| **0.8, 0.20 (used)** | **49 %** | **3.3 %** |
| 1.0, 0.25 | 64 % | 6.4 % |
| 1.5, 0.40 | 81 % | 18.8 % |

At 0.8 px / 20 % the share of true pairs among the candidates rises from 6 % to about 48 %. This is the setting
that maximises (true kept)/√(random kept). No setting keeps 90 % of the true pairs: the residuals' tails are wide,
mostly from blended detections.

**S2b: the model against the Planes** (`tests/s2b_planes_check_out.txt`, `.png`; a check added to the plan). The
Planes were recorded with T1's focus and aperture (your answer 3), so the board's dot edges are blurred by the same
defocus. Each dot is placed where its line of sight meets its plane (C2a). Comparing P0e's edge blur with the
model's width there:
- **cam1:** along u 1.17–1.25 × the model, along v 0.78–0.89 ×.
- **cam2:** 1.05–1.20 × on both axes.
- **Slopes with depth along u:** cam1's measured +0.159 against the model's +0.1585 px/mm; cam2's −0.075 against
  −0.088.
- **Slopes along v:** the model is 2.6× too steep for cam1 and 0.6× for cam2.
- **Judged:** within the ~30 % expected, since printed edges are not particle images. The earlier fit (A 8.2 mm)
  was off by 1.9–3.1× along cam1's u, with the slope's sign wrong.

## 5. What you should know, and open issues

1. **About half of T1's long tracks are ghosts.** Ways to reduce them, roughly in order of effect:
   - **A third camera,** the usual remedy: random triples that agree are rare.
   - **A better calibration.** T0's error pattern (0.5–1 px) spreads the true matches over ±2 px of the epipolar
     curves, which needs the 1.5 px tolerance. A disparity correction from the tracers themselves (what VSC does,
     for PINHOLE cameras only today) would narrow it. A PINCYL version is not in this plan.
   - **A stricter depth cue.** 0.5 px / 20 % keeps 29 % of true pairs and 1.3 % of random ones (S2's scan): purer
     but fewer.
   - **Filtering the tracks after tracking,** by length or by the swirl test. This biases the statistics towards
     the expected flow, so use it with care.
2. **The calibration** (Phase C report §7):
   - f is not determined;
   - the wand's and the board's scales differ by 0.4–0.5 %;
   - the board's stage steps were 2.54 and 2.46 mm (0.1 in), not 0.125 in.
3. **A library issue, not fixed:** with the thorough start search (`n_final` 6), `calibrate` can choose a wrong
   minimum (Phase C report §3). The case uses `n_final` 2.
4. **The shape model** leaves two things:
   - a residual trend with depth, up to 0.9 px over the depths in cam1's widths;
   - wide tails, mostly blended detections, so no tolerance keeps 90 % of the true pairs.

   Its flux law is empirical.
5. **pytest:** `test_refract_oracles.py::test_vendored_cylinder_oracle_matches_notes_repo` fails since your 2 Oct
   commit to the notes repo (8a76a83). Re-copy `code/project_cylinder.py` to `test/refs/`. It does not depend on
   this work.
6. **GUI:** the new tracer keys are in config.json only; the GUI has no controls for them (decision D7).
7. **Your GUI build** (`build/Release`, `build-py/Release`) is still the old one. Rebuilding it with
   `build_local.py` waits for your OK.
