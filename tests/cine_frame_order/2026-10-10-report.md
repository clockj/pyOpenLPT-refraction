# Fix of the .cine frame reading in image preprocessing: report (Part A)

10 October 2026. Plan: `2026-10-10-plan.md` (approved on 10 Oct). Part A is done and every test passes. Part B, the
renumbering of the 20260727 images (B2, your choice), has not started; it changes files on X:.

## 1. Summary

- **The bug:** pyOpenLPT's image preprocessing handed pycine the camera's frame number where pycine expects a position
  counted from 1, and pycine takes 0 as 1.
  - **The GUI batch** reads in chunks of 256. Its first chunk was right; every later chunk started one frame early. So
    file 256 repeated frame 255, later files were one frame late, and the last frame was lost.
  - **This is how all 20260727 images were made** (`cases/stb_20260727_tracer_all`, report section 10).
- **The fix:** one function, `io.read_cine_frames(cine_path, frame, count=1, header=None)`.
  - It turns the camera's frame number into pycine's position, `frame − FirstImageNo + 1`, which is always 1 or more.
  - It checks the range.
  - All eight reads in `io.py` and `view.py` now use it. Nothing else changed.
- **Tests (all pass):**
  - **F1, synthetic videos through the real pycine:** 37 of 37 checks pass on the fixed code. On the old code the 14
    checks of the GUI and command-line paths fail, exactly as the bug predicts.
  - **F2, the real videos:** the new function returns exactly the stored frames.
  - **F3, the conversion:** with the cached background, it reproduces the old files pixel for pixel, one frame later
    from 256 on. So renumbering the old files (B2) gives the same images as reconverting.
  - **F4:** pyOpenLPT's 21 preprocessing tests pass.

## 2. The change

`modules/image_preprocessing/io.py`:
- **new `read_cine_frames`:** the docstring explains pycine's numbering. It raises `ValueError` outside the video and
  `ImagePreprocessingIOError` if pycine returns fewer frames than asked;
- **`read_cine_frame`** (command-line conversion) now uses it;
- **`compute_mean_background_from_cine`** (command-line background) now uses it, with the header read once.

`modules/image_preprocessing/view.py` (the GUI) imports `read_cine_frames` and uses it at:
- the batch's chunk read and its per-frame fallback;
- the background average's chunk read and its fallback;
- the preview (`_read_image`).

The `pycine` import stays, as the flag that says whether pycine is installed.

## 4. Seen on the way, not changed

- **pycine 0.3.2 itself:**
  - its `start_frame` docstring says 0 is the first frame, but the code counts from 1;
  - its `start_frame_cine` has the same off-by-one;
  - negative positions wrap to the end of the file.

  The fix only avoids these; pycine is not patched.
- **`compute_mean_background_from_cine`'s `start`** (default 0) is a frame number in the camera's numbering, so for a
  video numbered from below 0 it skips the frames before 0. The GUI passes its batch start, a place in the list, as
  `--bg-start`. The two agree when the numbering starts at 0, as in every 20260727 video.
- **OpenLPT_GUI** (`D:\Bubble_Reconstruct\OpenLPT_GUI`) has the same `view.py` and `io.py`. As you chose, it is not
  changed.
