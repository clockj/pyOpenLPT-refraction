## The bug (D3)

- **What the code does:** pyOpenLPT lists a video's frames by the camera's numbering (`FirstImageNo` …) and passes
  that number to pycine's `read_frames(start_frame=…)`.
- **What pycine does with it** (pycine 0.3.2):
  - it reads stored frame `start_frame − 1`, and takes 0 as 1;
  - it takes a negative position from the end of the file.
- **The result in the GUI batch** (chunks of 256), checked on the videos of two runs:
  - file 256 repeats stored frame 255;
  - after it, file j holds stored frame j − 1;
  - the last stored frame is never written.
- **Eight calls make the same mistake:**
  - `view.py` 206 and 245 (the batch);
  - `view.py` 412 and 438 (the background average);
  - `view.py` 2193 (the preview);
  - `io.py` 358 (the command-line conversion, frame by frame, so its copy is at frame 1);
  - `io.py` 465 and 477 (the command-line background).
- **The group's OpenLPT_GUI** (`D:\Bubble_Reconstruct\OpenLPT_GUI`) has the same `view.py` and `io.py`.

## Part A: the fix

- **One function** in `io.py`: `read_cine_frames(cine_path, frame, count=1, header=None)`.
  - `frame` is in the camera's numbering, and the function checks that it is in range.
  - It reads from position `frame − FirstImageNo + 1`. That position is always 1 or more, so pycine's 0 and negative
    positions never occur.
- **All eight calls use it.** Nothing else changes:
  - the lists keep the camera's numbering;
  - files keep their names (`img<n>.tif`, n = place in the list);
  - the processing is untouched.
- **pycine itself is not changed.**

### Tests (`tests/cine_frame_order/`, each with its results beside it)

- **F1, synthetic videos through the real pycine.** The test writes small .cine files: 600 frames of 16 × 8 pixels,
  16-bit, each frame carrying its stored position in binary in its pixels, so the number survives any processing to
  8 bits. `FirstImageNo` is 0, 1, 5 and −300.
  - **The old code** reproduces the copy at 256 (`FirstImageNo` 0). This documents the bug.
  - **The new function** returns the right stored frame for every frame, read one at a time and in chunks of 256, 128
    and 100.
  - **The GUI batch worker (run without a window) and the command-line runner,** on these videos: every output file
    holds the right frame, and the last one is there.
- **F2, the real videos (read only).** Frames 0, 1, 255, 256, 257 and 12,604 of 35Hz_r_b_1, cameras 0 and 1, read by
  the new function, are equal to the stored frames read straight from their file offsets.
- **F3, the new conversion reproduces the old files.** Inputs: the run's cached background (`imgFile\background_cache.mat`:
  backgrounds, bit shifts 1/2/1/2, invert on), and the grey-level range and denoise setting recovered from the old
  frames 0–255 (which are right). Converting 35Hz_r_b_1, camera 0, frames 250–262 and 12,603–12,604 must give:
  - **files 250–255:** the same pixels as the old ones;
  - **file 256:** the same pixels as old 257 (stored frame 256), and so on;
  - **file 12,604:** the video's last frame, which the old files lack.
- **F4:** pyOpenLPT's existing preprocessing tests still pass (`tests/test_image_preprocessing_io.py`,
  `tests/test_image_preprocessing_cli.py`).

## Part B: putting the 20260727 images right (after Part A passes)

Two ways to the same images; you choose.
- **B1, reconvert (your choice so far):**
  - **How:** a script in `cases/stb_20260727_tracer_all/reconvert/` does what the GUI batch does: chunks of 256 through
    the fixed function, the same processing function, parallel processing and writing. It uses each run's cached
    background and settings, so no GUI clicking is needed.
  - **Where:** to `<run>\imgFile_new\`. After the checks, `imgFile` becomes `imgFile_old`, kept until you delete it,
    and `imgFile_new` becomes `imgFile`.
  - **Time:** the first conversion took about 47 min per camera, reading the video at 22 MB/s and writing at 10 MB/s
    over the network. So about 3 h per run, 1.5–2 days for all twelve, limited by the network.
- **B2, renumber the old files (same pixels, about 20 min per run):**
  - **Time, measured after approval:** a rename on X: takes 48 ms one at a time, 21 ms with 16 threads in one folder,
    and 8.5 ms with 16 threads each in its own folder. The plan first said "minutes per run". The 12 runs × 3 folders
    × 4 cameras need 1.78 million renames, about 4 h with 16 folders at a time.
  - **Why it is the same:** with the cached background, a reconverted file i is the old file i + 1, from 256 on (F3
    checks this).
  - **How:** move old file 256 aside, then rename 257 → 256, 258 → 257, … Renames on the server copy no data, and a
    log of them allows an undo.
    - **First plan:** rename into `<run>\imgFile_new\`, then swap the folders.
    - **Refined after approval:** rename in place, in increasing order, with the copy moved to
      `<run>\removed_copy256\<folder>\camN\`. There is no folder swap, and an interrupted folder has one gap and
      resumes from it.
  - **The last frame:** convert only frame 12,604 with the fixed code.
  - **What changes on X::** the old files themselves are renamed, not copied.
- **Checks either way, per run:**
  - 12,605 files per camera;
  - frames 0–255 unchanged;
  - frame 256 no longer equals 255;
  - a sample of later frames equals the old frame + 1, or for B2, the rename log.
