## Phase A — the slowdown (suggestion 1)

**A1. Small matrices without the heap.**
- **The change:**
  - `Matrix<T>` keeps up to 9 elements inline (`T _sbo[9]`); `_mtx` points there when n ≤ 9, and to the heap
    otherwise.
  - This covers `Pt2D`, `Pt3D`, `Line3D` and 3×3 matrices. Images stay on the heap.
  - The buffer size is a threshold, not a limit: any larger matrix takes the heap path exactly as today.
  - The copy constructor, assignment, `clear()` and `create()` handle both cases. No move operations are added in A1,
    so copying behaves exactly as today (moves stay copies, as now).
  - The API does not change. `_mtx` is private and used only in `Matrix.hpp`, plus `data()`.
- **Memory safety (checked in the code, 5 Oct):**
  - **One place picks the storage.** Every size change goes through one helper that compares the size with the
    buffer. `create()` and `operator=` already do. `operator*=` resizes on its own (`delete[] _mtx; _mtx = new T[_n]`,
    `Matrix.hpp` lines 428–436): with the buffer that `delete[]` would free memory never allocated, so it is routed
    through the helper. There is no other resize (no `resize`, no `push_back`).
  - **`delete[]` only for heap storage** (`_mtx != _buf`). The default constructor sets `_mtx = nullptr` (today it is
    left uninitialised), and assignment returns early on self-assignment.
  - **No raw copies.** `_mtx` points into its own object, so a byte-wise copy would point into the original. The class
    has its own copy constructor and assignment, so containers always call them. The only `memcpy` calls in the
    sources copy raw image buffers in `ImageIO.cpp`, never a `Matrix`.
  - **Out-of-range indices.** `operator()`/`operator[]` don't check today. An index past the end corrupts the heap now;
    with the buffer, an index below 9 would land silently in its unused part. A build option makes both check against
    `_n`. The baseline runs with it first, so any existing out-of-range access is found and fixed before the switch.
  - **Layout change.** `sizeof(Matrix)` changes, so everything that includes `Matrix.h` is rebuilt from clean.
- **Parallel code:**
  - Each object owns its storage; there is no shared pool, static scratch matrix or `thread_local` buffer.
  - The parallel loops already give each thread its own objects: `Shake` works on `objs[i]` and locals, and
    `StereoMatch::match` on locals and per-thread buckets. No `static` or `mutable` `Matrix` members exist.
  - So A1 changes no sharing. It removes the one thing all threads share today for every point, the process heap.
  - A local matrix keeps its numbers on its thread's stack (+72 bytes each). No stack arrays of points exist, and
    the matching search is only as deep as the camera count.
  - `new` stays for matrices larger than the buffer (images, OTF tables, the fits in VSC) and for everything that is
    not a `Matrix` (`Tracer2D` objects, `std::vector` buffers, `Frame` copies; B3 handles some of those).
- **Why:**
  - Every `Pt2D`/`Pt3D`/`Line3D` temporary now costs a `new`/`delete`. One plate `lineOfSight` call does about 15
    pairs, and one `myMATH::triangulation` about 20 (two of them 3×3).
  - Every tracked point keeps 11 heap blocks for its track's life: the `Tracer3D`, its `Pt3D` array, the list of
    2-D views, 4 `Tracer2D`, 4 `Pt2D` arrays. After A1 it keeps 6.
  - T4d showed a fragmented heap slows the geometry code 1.5–1.9× on one thread; with 26 threads it gets worse.
- **Memory:**
  - The buffer makes every `Matrix` 96 bytes instead of 24 plus a heap block.
  - A stored track point (one `Pt3D`, four `Pt2D`) grows by about 190 bytes. In this case that is about +1 GB at
    frame 500 (private bytes 7.5 → about 8.5 GB), and less with `save_interval` 200.
  - A 3-element buffer covers points and lines with slightly less memory than today (about −0.3 GB), but leaves the
    3×3 matrices of `myMATH::triangulation` on the heap.
  - **Choice:** the buffer size is one constant. B300 runs with 3 and with 9, and the faster is kept (3 if they tie).
- **Checks:**
  - unit tests of `Matrix`, `Pt2D`, `Pt3D` (copy, assign, self-assignment, arithmetic, `list(Pt2D)`, large matrices,
    `Image`), with every storage change: small → small, small → large, large → small, large → large of the same and of
    a different size, `operator*=` crossing 9 elements, copies during `std::vector` growth, `Line3D` and `Object3D`
    copies and moves;
  - the index-checking build on the C++ tests (`OPENLPT_BUILD_TESTS`), `pytest` and frames 0–10, before and after;
  - AddressSanitizer (MSVC 2022 `/fsanitize=address`) on the C++ test executables, before and after: it reports
    writes past heap blocks, use after free and wrong `delete[]`;
  - identical outputs (frames 0–50) at 26 threads, and the same run twice. MSVC has no thread sanitizer, so the
    evidence for the parallel code is the design, the code check above and these runs;
  - B300 and R300.
- **Success:**
  - the time per frame grows by less than 20 % over B300's 300 frames (today: 6 → 17.6 s);
  - R300's fresh and aged processes are within 20 % of each other;
  - identical results.

## Phase B — stereo matching (suggestion 2)

**B0. Measure first.**
- Counters per IPR round:
  - lines of sight computed;
  - projections;
  - candidates on the 2nd, 3rd and 4th camera;
  - search steps;
  - matches before and after pruning.
- Times: building, checking, pruning, triangulating.
- Off by default; on through a setting (`ipr.profile`). One extra log line per round.
- It shows where matching spends its time today and checks B1–B5.

**B1. Compute each line of sight and each epipolar line once per round.**
- **Today:**
  - `buildMatch`, `enumerateCandidatesOnCam`, `checkBackProjection`, `checkMatch` and
    `selectSecondCameraByLineLength` recompute the line of sight of the same detection for every candidate.
  - They also re-project two points of it into the other cameras (two refractive projections per line) for every
    candidate and every back-check.
- **The change:**
  - at the start of `match()`, compute in parallel the line of sight of every detection of the active cameras;
  - also compute its 2-D line in each other active camera: about 70,000 detections × 3 cameras, about 0.4 million
    projections per round;
  - every step then reads these tables.
- **Results:** identical, the same values.
- **Expected:** matching several times faster (B0 measures it).

**B2. Anchor the epipolar line inside the view volume.**
- **The change:** draw the line through the images of the points where the line of sight enters and leaves the view
  volume (clipped to the box), instead of points 1 and 2 mm past the far wall.
- **T2's numbers with perfect data:**
  - 4-camera particles findable at 2 px: 37 % → 91 %; at 3 px: 54 % → 100 %.
  - The 3-camera sets: 41–44 % → 91–97 %.
- **B2b, if misses remain:** a line in three points (entry, middle, exit) with two segments; that needs `IDMap`'s
  strips per segment.
- **This changes results** (more matches). Checked by:
  - T2's script with the new rule;
  - T3 on raw frames (4-camera matches at 2 px);
  - B300 (objects, tracks, removals, time).

**B3. No allocations in the search.**
- The depth-first search copies five vectors per candidate (`Frame nxt`).
- Per-thread scratch buffers and a stack of choices replace them. Results identical.

**B4. A k-d tree for removing repeated objects (`STB::checkRepeat`).**
- **Today:** it compares every new IPR object with every active long track's last point: about 10,000 × 13,000 pairs
  per frame, 0.36–0.6 s.
- **The change:** a radius query on a k-d tree (nanoflann, already used for linking) takes about 0.01 s. Results
  identical.

**B5. Pruning.**
- `pruneMatch` runs on one thread, sorts all candidates and builds one vector per 2-D point.
- If B0 shows it matters: flat arrays instead of vectors of vectors, one sort. Results identical.

**Your question, data structures and trees:**
- **Matching already has a spatial index.** `IDMap` is a uniform grid of 4 × 4 px cells per camera.
  - A line's ±tol band is turned into row spans, and only the cells in them are visited.
  - For "the points within a band along a line" that is the efficient structure.
- **A tree would not help here.** k-d trees and R-trees are made for nearest-neighbour and radius queries around a
  point. A long thin band crosses many tree nodes, so a tree would not be faster, and it costs more to build every
  round.
- **The time goes around the index:**
  - recomputing refractive projections and lines of sight for every candidate (B1);
  - heap allocations (A1, B3);
  - the serial pruning (B5).
  - B0's counters will confirm this split before the changes.
- **A tree does help** in removing repeated objects (B4), a 3-D radius query where a k-d tree beats comparing all
  pairs.

## Phase C — the short-track linking radius (suggestion 3): deferred, your decision

**What it is:**
- In the convergence phase a short track links to the nearest new object within "Avg interparticle spacing" = 30
  voxels of its predicted position: 3.9 mm, growing to 5.7 mm.
- Particles move 0.08–0.15 mm per frame.
- 70–85 % of the 2–3-point short tracks move more than 0.5 mm per frame, so they are chance links.
- About 1,270 of them per frame reach four points and are then removed by the linear-fit test.

**What it would take:** lower the setting to about 5–8 voxels (0.65–1.0 mm), a config change only, tested on B300.

**When:** after Phases A, B and D, when their effect on the spurious tracks is known.

## Phase D — the linear-fit test (suggestion 4), after A and B

**D1. Drop the failing point before a track is saved as lost.**
- In `runConvPhase`'s pruning loop, a track that fails `checkLinearFit` loses its last object and frame before it moves
  to `_long_track_inactive`. It is still saved only if it keeps at least 7 points.
- **Why:** each lost track now ends with its 3 px outlier (T6c).
- **Effect:** tracking does not change, because the track is removed either way; only the saved data get cleaner.

**D2. The limit as a setting:** `linear_fit.max_residual_mm`, by default 0.05 (today's `MAX_ERR_LINEARFIT`).

**D3. A prediction-based test, selectable** (`linear_fit.mode`: `"fit"`, today's, or `"prediction"`).
- **The test:** the distance of the new point from the extrapolation of a least-squares line through the previous 4–5
  points, against `linear_fit.max_prediction_error_mm`.
- **Why:** today's fit includes the new point, so it shows only about 0.3× of a jump. A 0.05 mm residual corresponds to
  a jump of about 0.17 mm. A prediction-based limit means what it says.
- **How the limit is chosen:**
  - replay the test offline on T4's and T5's saved tracks;
  - take the distribution of the test value on the points that passed (noise: 0.005–0.007 mm per axis) and on the
    deletions (jumps of 0.18–0.19 mm);
  - choose the limit that falsely removes under 0.1 % of good points and still catches the jumps.
  - Expected: about 0.05–0.08 mm prediction error.
- **Checks:**
  - the offline replay (deletions and keeps per rule);
  - B300 with the chosen setting (removals, track lengths, saved tracks free of end outliers).
- **Not planned: loosening the limit.** T6c showed that the jumps are real losses, so a looser limit keeps outliers,
  not particles.

## Phase E — track prediction (your new questions)

**Today:**
- `STB::predictNext` predicts the next position of every active long track in one parallel pass per frame.
- Per axis, it fits LMS ("Wiener-like") coefficients to a single sample of up to 6 positions and extrapolates.
- It takes 0.00–0.01 s per frame. So a faster or "one-step-for-all" predictor cannot make tracking measurably faster:
  it already is one step for all tracks, and it is already negligible.

**Its accuracy matters:**
- A prediction must fall within the shake range (±0.25 voxel = ±0.032 mm here) for shaking to lock onto the right
  particle.
- Predictions also guide short-track linking.

**A concern:** the LMS fit depends on the coordinates' absolute values, so it is not translation-invariant.
- It adds 10 mm when a coordinate is within 1 mm of 0.
- So its error can depend on where a particle is, and on where the calibration put the world origin.

**E1. Evaluate offline first (no code change).** On T4's and T5's saved long tracks, replay one-step predictions:
- **The predictors:**
  - today's predictor, ported to Python and checked against the C++ on a sample;
  - least-squares polynomials (linear and quadratic) over the last k points;
  - Kalman filters with constant velocity and with constant acceleration.
- **Metrics:**
  - the one-step error (median, p99), overall and over the view volume;
  - for the deleted tracks: whether the failing point sits where today's predictor sent it, that is, whether a bad
    prediction caused the jump.

**E2. Kalman parameters.**
- **Measurement noise r:** from the tracks' measured position noise (T6b: 0.005–0.007 mm per axis).
- **Process noise q:** from their measured acceleration and jerk.
- **Refinement:** fit both on half of the tracks, by the lowest one-step error (or the highest innovation likelihood),
  and test on the other half.
- **Units:** mm and frames, so the defaults carry over to other frame rates and voxel sizes; overridable in the
  config.
- **Answer to your question:** the parameters are set from the data, not by hand.

**E3. Implement only what E1 shows to be clearly better.**
- **Threshold:** for example at least 30 % lower p99 error, or fewer jumps caused by the predictor.
- **Setting:** `prediction.method`: `"wiener"` (today), `"poly"` or `"kalman"`.
- **Check:** B300 (removals, track lengths, data yield).

## Phase E: the detailed steps (approved 6 Oct)

**Your instruction (6 Oct):** "go on for phase E." Phase D (the linear-fit test) is not done first: E1 and E2 do not
depend on it.

**What the code does today** (read again for this phase):
- **The formula:** `STB::predictNext` predicts each axis separately from the last m + 1 positions, m = min(n − 1, 5).
  - Its "LMS" loop stops after one pass, because one normalised step solves its single equation exactly.
  - So the prediction is p = y_m · Σ y_j y_(j+1) / Σ y_j² (j = 0 … m − 1).
  - 10 mm is added to the axis first when |y_m| < 1 mm.
- **Far from the origin** this tends to p = y_m + (y_m − y_0)/m, the mean step over the last m frames.
- **Near the origin it does not.** For a coordinate 1–3 mm from 0, moving 0.1 mm/frame, the prediction is pushed
  away from 0 by 0.009–0.037 mm on that axis; at 10 mm, by 0.003 mm. Every axis of the view volume crosses 0.
- **Constant velocity is assumed.** At T6c's 0.008 mm/frame², the mean step misses by about 3a = 0.024 mm. The
  shake's first step is 0.25 voxel = 0.032 mm.
- **Short tracks** do not use it: `linkShortTrack` predicts with the neighbouring long tracks' last step.
- **Cost:** 0.0001 s per frame on average in `b300_final3` (the clock shows 0 or 0.01 s), against 2.5 s per frame.
  It already is one parallel pass over all tracks. So a faster or batched predictor cannot make tracking faster; that
  answers your second question without a test.

**The data:** the saved long tracks (active at the last save, left the volume, lost) of three runs. The prediction
code is the same in all three.
- T4 (new camFiles, frames 0–500) and T5 (old camFiles), on X:, from the code before this campaign;
- B300 (`runs/b300_final3`, frames 0–300), from this campaign's final code.
- **The points scored:** every point from the fifth of its track on (index ≥ 4). STB got each of them by shaking a
  prediction; the first four came from linking.
- **The jumps:** the last point of a lost track that failed the linear-fit test is scored separately.

**E1a. The port.** The Python copy of `predictNext` against the C++ function itself, called through the module
(`STB.predictNext`, `build-py/Release`).
- **Cases:** 20,000 histories sampled from B300's tracks (3–7 points), and edge cases: an axis at 0, ±0.999999, ±1
  and ±1.000001 mm, negative coordinates, a particle at rest, 3-point tracks.
- **Judged by:** agreement to 1e-12 mm.
- The short derivations above (the one-pass loop, the limit far from the origin, the bias near it, the misses under
  acceleration) are checked with SymPy.

**E1b. The replay:** each predictor predicts every scored point from the points before it.
- **The predictors:**
  - W: today's (the port);
  - MD: W's limit far from the origin (the mean step over the last m frames); W against MD is the cost of the
    origin dependence;
  - LIN-k: least-squares lines through the last k points (k = 3, 4, 6, 8, 10, 15), extrapolated one frame;
  - QUAD-k: least-squares parabolas through the last k points (k = 5, 6, 8, 10, 15, 20), extrapolated one frame;
  - KF-CV and KF-CA: Kalman filters with constant velocity and with constant acceleration, per axis, over the whole
    track from a diffuse start, with E2's parameters.
- **Measures** of the 3-D error |prediction − point|:
  - median, RMS, p90, p99 and p99.9;
  - the shares above 0.032 mm (the shake's first step), 0.064 mm (about 1 px) and 0.1 mm.
- **Splits:**
  - by run;
  - by the number of points before the prediction: 4, 5, 6, 7–10, 11–30, > 30;
  - by each axis's distance from 0: < 1, 1–3, 3–10, ≥ 10 mm (W's origin dependence);
  - over the view volume: 6 × 6 bins per plane.
- **The jumps:** for every lost track of ≥ 9 points whose last point failed the linear-fit test:
  - where W put the prediction (|last point − W|), and where the other predictors put it;
  - compared with the same distances on ordinary points.
  - If the last point sits at W's prediction while the better predictors place the particle elsewhere, the
    prediction caused the jump.
- **A bias to keep in mind:** the scored points are not independent of W.
  - Each one is W's prediction after shaking. E1c measures how strongly the start pulls the result.
  - The tracks are the ones W kept. E1d compares the predictors without that selection.

**E1c. How accurate must a prediction be? (The shake capture test.)** With the current module and the C++ shake, on
real images:
- **The reference:**
  - B300's active long tracks at frame 300, predicted with `predictNext`;
  - cut as `runConvPhase` cuts them (view volume, at least two cameras);
  - shaken together on frame 301's images (`Shake.runShake`).
  - This reproduces STB's own frame 301. It is checked against a restart run that loads the same tracks and runs
    frame 301 (`runs/r301_e1c`: stbrun.py, `--load 300 --load-from b300_final3`). The shaken positions must be the
    same, to the 1e-6 mm of the saved tracks.
- **Moved starts:**
  - Every prediction is moved by δ in a random direction (δ = 0.005, 0.01, 0.02, 0.032, 0.05, 0.075, 0.1, 0.15 and
    0.2 mm), and all are shaken together again.
  - Per δ: the share that ends within 0.005 mm of the reference (captured), the share flagged ghost or repeated, and
    how far the rest end.
- **The best alternative's predictions** as starts, measured the same way.
- **What it decides:**
  - the capture radius, against the predictors' p99 errors: if every predictor already lands well inside it, a better
    predictor changes little;
  - the pull of the start on the result at small δ, which is the bias of E1b.

**E1d. Synthetic tracks with known truth.**
- **The tracks:** moving at the measured speed and acceleration, with the measured noise (E2's fit), placed over the
  view volume.
- **Checks:**
  - **the Kalman code:** with the generating model's parameters it has the lowest mean squared error, and its errors
    match its own predicted variance; with q = 0 it equals the least-squares fit through all points (to 1e-9);
  - **W's origin dependence,** against the numbers above;
  - **the ranking of the predictors** against the true positions, without shaking.

**E2. Kalman parameters.**
- **r:** the tracks' position noise per axis (T6b's second-difference estimate).
- **q:**
  - From a diffuse start the predictions depend only on the ratio λ = q/r.
  - So λ is scanned (1e-6 to 1e2) for each model. It is chosen by the mean squared one-step error on half the tracks
    (split at random by track), and tested on the other half.
  - **Cross-check:** the innovation likelihood fixes q and r together. Its r must agree with the measured noise.
- **Transfer:** each run's λ is applied to the other two runs, to see whether one default serves all.
- **Units:** mm and frames.

**E3. Only if E1 shows a clear gain.**
- **Threshold:** either of
  - the best alternative's p99 one-step error at least 30 % below W's, on all three runs (test half);
  - a clear share of the jumps caused by W (E1b with E1c).
- **Then:**
  - **The setting:** `predictNext` gets the chosen method as a setting: `"prediction": {"method": "wiener" | "poly" |
    "kalman", ...}` in config.json, `prediction_method = ...` lines in config.txt. The default is "wiener", today's.
  - **No new state:** it stays a function of the track's points, so a restart predicts the same.
  - **Checks:**
    - the C++ predictors against the Python ones, as in E1a;
    - S50 with the default: identical to `s50_final3`;
    - B300 with the new method, against `b300_final3`: removals, linear-fit failures, track lengths, tracked points,
      time per frame.
  - **Built** in a campaign build (`build_variant.py`). The builds the GUI runs (`build/Release`, `build-py/Release`)
    stay as they are until you decide.
- **Otherwise:** no code change. The report gives the numbers and the answers to your three questions.

**Files:**
- **Scripts:** `predictors.py` (the predictors), `e1a_port_check.py`, `e1b_replay.py` (E1b and E2),
  `e1c_shake_capture.py` and `e1d_synthetic.py`.

- **Report:** section 10.

## E4: the origin-free predictor (approved 6 Oct)

**Your instruction (6 Oct):** "Go on and test for the origin free predictor" (report 10.6, first option).

**The change** (`src/srcSTB/STB.cpp`, `STB::predictNext` only):
- Each axis is predicted by the mean step over the last m frames: p = y_last + (y_last − y_(last−m)) / m, with
