# A pixel size per camera in the wand tab — report

8 October 2026. Plan: `2026-10-08-plan.md` (the case plan's Phase G, approved with it).

You asked:

> camera 3 is Phantom v2640, which has a higher resolution; so when you extract for balls, you probably need to set
> different pixel size for that camera, and you should update gui for that option as well.

## Result

**The GUI now takes a pixel size per camera, and with it detects run 20261008's three cameras with one setting.**
- **Without it,** cam3 kept no frame: the rod opening that suits cams 1–2 (51 px) leaves cam3's rod attached, so it
  finds one blob.
- **With pixel sizes 20 / 20 / 13.5 µm,** cam3's settings are scaled by 1.48 and it keeps 19 of 24 test frames,
  cams 1–2 20 and 16.
- **With no pixel sizes,** the detection is bitwise the same as before.

**What changed for the user:**
- **The camera table** of the wand tab has a column **Pixel (µm)**, empty by default.
  - **Detection:** set it for every camera, and the Radius Range, Rod opening and Rod mask are in the first camera's
    pixels. A camera with pixels p gets them multiplied by p₁ / p, in Test Detect, Process Frames and the axis
    points. The overlap guard (3 px) stays. With no pixel sizes, or all equal, nothing is scaled.
  - **f in mm:** the cylinder and flat-window results pages print each camera's f in mm with its own pixel size. The
    Tube Settings' single "Pixel size" box, which did only that, is gone.
- **Cameras that saved different ranges of images are lined up.** When every loaded folder holds a Phantom header
  (`.chd`) and their first image numbers differ, the lists are cut to the images every camera saved, so the i-th
  frames are simultaneous. The status line says how many were dropped. Run 20261008/T0 needs this: cam3 saved
  images 2396–13000, cams 1–2 0–13000. Loading all files would have paired frames 2,396 apart.
- **The user guide** (`WAND_CALIBRATION_USER_GUIDE.md`) describes the column and the alignment. Its HTML and
  screenshots are not regenerated.

**The code:**
- `wand_calibration/wand_calibrator.py`:
  - `scale_detect_settings`;
  - `phantom_image_numbers` and `align_by_image_numbers`;
  - the two detection workers and `detect_single_frame` / `detect_wand_points_generator` take `cam_scales`
    (default None: unchanged).
- `view.py`:
  - the column, `_wand_pixel_sizes` and `_wand_cam_scales`;
  - `_align_wand_images`, called after each Load and after Num Cameras changes;
  - the scaled Radius Range limit;
  - the jobs' pixel sizes (`_wand_pixel_mm_for`);
  - the Tube Settings' box removed.
- `curved_calibration/cylinder_wand_gui.py`, `plate_wand_gui.py`: `Job.pixel_mm` may be a list
  (`pixel_mm_list`).

Only Python changed; no rebuild is needed. Nothing is committed.

**G1's failed check.** It compared the GUI's scaled cam3 settings with the slightly different ones the case set by
hand, so a difference was expected.
- **The settings:** the GUI gives 29.6–103.7 px, opening 77, mask 41.5 px; the case uses 30–105 px, opening 77,
  mask 42 px.
- **The outcome:** both keep the same 19 frames. The centres agree to a median of 0.0004 px, and at most 0.11 px
  against the 0.05 px I had set.
- **The cause:** the 0.5 px wider rod mask and the 2 px wider background window change which edge points one ball's
  fit uses.
- **Why it doesn't matter:** that is well below the calibration's 0.5 px residuals. The scaling itself is exact (G1's
  second check).
- **Kept as it ran.** I didn't loosen the criterion afterwards.

**G4c: the table was too wide, before this change too.** G4b's first picture
(`first_run/g4b_detection_panel_before_widths.png`) showed the table cut after Width.
- **The cause:** the spin boxes ask for 125–139 px each, so the columns needed 633 px in a 336 px table (504 px
  before the Pixel column was added). Width and Height had already been behind a horizontal scroll bar; the new
  column joined them.
- **The fix, in `view.py`:**
  - the table's cells have no spin buttons and no padding (typing and the mouse wheel still work);
  - Focal, Width and Height have fixed widths of 62, 60 and 60 px, and the Pixel column takes the rest;
  - the pixel size shows without trailing zeros (20, 13.5).
- **The result:** every value shows in full at 1700 × 1080, 1500 × 900 and 1200 × 700 (`g4c_table.png`; the measurements
  before the fix are `g4c_table_width_before_out.txt` and `g4c_table_width_nobuttons_out.txt`).
- **Reruns:** G4 and G4b ran again on the fixed table and passed. Their first runs are in `first_run/`.
- **G4's own pictures** (offscreen, `view.grab()`) showed no text, because offscreen Qt has no fonts. I deleted them
  and the two lines that took them; G4b takes the pictures.

**Not tested:** the plate (flat-window) calibration with pixel sizes. Its job takes the list through the same
`pixel_mm_list`, and the GUI path that fills it is G4's.
