# Plan: the reprojection errors' distributions on the GUI's results page (7 Oct 2026)

**Your request:** "for the gui, please add 2d projection error pdf for your wand calibration reports: du, dv, 2d
magnitude."

**How I read it:** the probability density of each camera's reprojection errors goes on the results page that the
GUI writes after every wand calibration (the Report tab), for all three models: Pinhole, Pinhole + flat windows and
Pinhole + cylinder. It shows three quantities:
- **du and dv:** where the calibrated model puts a ball minus where it was detected, along the image's x and y, in px;
- **|e| = √(du² + dv²):** the error's 2-D size.

The T0 and T2 case pages, which already have a joint (du, dv) chart, are not changed.

## 1. What the page gets

**A new section, "The distribution of the reprojection errors",** after "How well each camera fits" (the residual
maps):
- **Three charts side by side** (one column on a narrow window): du, dv and |e|.
  - Each has one line per camera, in that camera's colour on the rest of the page.
  - The y axis is probability density (1/px), so each curve's area is 1.
  - du and dv share both axes, so their widths compare at a glance. Zero is marked.
- **A Linear / Log switch.** The log scale shows the tails: outliers, or a part of the image that the model misses.
- **Hover** shows a crosshair and a tooltip with the bin, and each camera's density and count there.
- **A caption:** the bin width and the detection counts.
- **A table per camera:**
  - detections used;
  - du and dv: mean and RMS;
  - |e|: median, RMS (the same number as "RMS (px)" in the cameras table), 95th percentile and maximum;
  - how many fall beyond the plotted range.

```
The distribution of the reprojection errors
<lead: what du, dv and |e| are; what noise looks like; what a shift, a width difference or a tail means>
● cam1  ● cam2                                                              [ Linear / log ]
 du (px)                         dv (px, + down)                  |e| = √(du² + dv²) (px)
 density (1/px)
 |          /\                   |          /\                    |     _
 |         /  \                  |         /  \                   |    / \
 |       _/    \_                |       _/    \_                 |   /   \__
 |  ____/        \____           |  ____/        \____            |  /       \____
 +------------+-----------       +------------+-----------        +------------------
 -2           0          2       -2           0          2        0         1        2
 Histograms in 0.04 px bins of the 3,928 and 3,928 detections the fit used ...
 Camera | Used | du mean | du RMS | dv mean | dv RMS | |e| median | |e| RMS | |e| 95 % | |e| max | Beyond the range
```

**Which detections:** every detection the calibration used, computed in Python. This is not the at most 2,500 per
camera that the residual maps draw. The detections the fit set aside are left out, and their number is in the
caption.

**Range and bins** (the same for all cameras, so the curves compare):
- **The range:**
  - du and dv share ±R, with R chosen so that at least 99.5 % of every camera's du and dv lie inside;
  - |e| runs from 0 to the same rule applied to |e|.
- **The bin width:** a round width from the Freedman–Diaconis rule (2 IQR n^(−1/3)) of the narrowest camera, so that
  even that camera's peak is resolved. It is kept between 20 and 150 bins.
- **The saved runs would get these** (measured today, read-only):

  | Run | du, dv range | Bins |
  |---|---|---|
  | T2 (real, tube) | ±2 px | about 100, of 0.04 px |
  | T0 (real, tube) | ±1.5 px | about 70 |
  | G3 (synthetic tube) | ±0.05 px | about 34 |
  | G8 (synthetic flat windows) | ±0.3 px | about 27 |

**What the report stores:** counts per bin (integers) and each camera's n. The page divides by n × the bin width, so
each curve's area is 1 minus the share beyond the range, which the table lists.

## 2. The code changes

1. **`modules/camera_calibration/results_page/page.py`:**
   - **New helpers:** `_error_pdf(...)` (about 50 lines: the range, bins, counts and statistics) and a small
     `_used_errors(data, names)`.
   - **The three adapters** (`report_from_cylinder`, `report_from_plate`, `report_from_pinhole`) each add one key,
     `error_pdf`, to the report. The docstring's schema lists it.
   - **Nothing else changes:** test H2 checks that every other key of the report is identical to git HEAD's.
2. **`modules/camera_calibration/results_page/template.html`:**
   - **The section above** (JavaScript, about 150 lines). It uses the page's existing colours, legend, tooltip and
     table helpers.
   - **It is drawn by `redraw()`,** so it follows the light/dark switch.
   - **It is skipped** when a report has no `error_pdf`, for example in a GUI that was started before the change.
3. **The user guide** (`WAND_CALIBRATION_USER_GUIDE.md`):
   - §6.3's list of what the page shows gains the distributions;
   - §6.4 gets one bullet on reading them;
   - the HTML is rebuilt with `make_user_guide.py`. The screenshots stay (guide_report.png shows the top of the page).

**Not touched:**

## 3. Tests

Everything goes in `tests/wand_report_error_pdf/`, results beside the scripts. `data/` holds the rendered pages
(untracked).

- **H1: `_error_pdf` on made-up errors.**
  - The counts equal numpy's histogram, "beyond" equals n minus their sum, and the statistics equal numpy's.
  - **Edge cases:**
    - a camera without detections;
    - None or NaN residuals;
    - all errors exactly zero;
    - a single detection;
    - eight cameras;
    - one camera 20× worse than the others: the range covers it, and the best camera still gets at least 4 bins
      across its IQR.
- **H2: the three adapters on saved results.** The inputs:
  - **tube:** G3 (synthetic) and the real T0 and T2 (read from X:; nothing is written there);
  - **flat windows:** G8 (synthetic);
  - **pinhole:** a synthetic 3-camera rig (W9's), with its true cameras.

  The checks:
  - the counts equal an independent recomputation from `calibration_data.json`;
  - each camera's |e| RMS equals the cameras table's RMS (`calibration_result.json`) within 1e-5 px;
  - for T0 and T2, the RMS of du, dv and the 2-D error equal the case pages' `err2d` (separate code, 6 Oct) within
    1e-9 px;
  - at least 99 % of each camera's du, dv and |e| lie inside the range;
  - every other key of the report is identical to git HEAD's `page.py` output.
- **H3: the pages in QtWebEngine** (as G4: the native platform, with the window off the screen).
  - **The pages:** G3, G8, pinhole, T0, T2, and a made-up 8-camera page.

    - the page loads, and the section has 3 charts with one curve per camera;
    - no console error, and no request but the page itself;
    - dark and light both render, and nothing overflows at 390 px;
    - the Log switch redraws without error;
    - a pointer over a chart brings up the tooltip;

  - **Screenshots** of the section in both themes. I look at them before reporting.
- **H4: an old report through the new template.** This is the case of a GUI started before the change. The page

- **H5: the GUI's Report tab** (as G4b) with the new T2 page: dark, and no JavaScript error. A screenshot of the
