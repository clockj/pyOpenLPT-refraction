## The answer

- **The library.** A camera in config.json can now carry a `"correction"`: a smooth field of pixel shifts, fitted
  between runs. Without it nothing changes: T1 and a synthetic set track byte for byte as before (L0). With it, every
  projection and line of sight goes through the field, and does so exactly (L1).
- **The GUI.** Run VSC on a tube or sphere project now fits each camera's correction from the run's long tracks. It
  writes `camFile_VSC/vsc_cam<k>_corr_p<n>.txt` and points config.json at them. A second click, after tracking again,
  adds a second pass. Pinhole and plate projects keep today's VSC.
  - Before this, the GUI's VSC read tube cameras as plain pinholes. It would have stopped, or replaced them with a
    wrong pinhole camera.
- **It reproduces the self-calibration study.**
  - **T1:** from scratch it gives the study's field to under 0.001 px.
  - **Synthetic sets with 2, 3 and 4 cameras:** it gives the study's fields to 0.0014 px. So the study's result
    applies to the module: one pass recovers 0.69, 0.80 and 0.89 of the error.
  - **The GUI's own two passes on T1:** they give the study's two-pass field to 0.05 px. The study's own two
    half-data fields differ by 0.18 px.
- **T1 through the GUI, end to end (section 3):** two passes at 1.0 px give the study's result through the library.
  - **Counts estimate:** 343 real long tracks at frame 100 against today's 296 (+16 %; the study's warped frames
    +11 %), and ghosts 36 % against 50 %.
  - **The residual across the epipolar curves:** 0.726 → 0.567 px.
  - **The swirl estimate** shows no gain, here as in the study.
  - **The library against the warped frames, with the same field:** they agree within 2 % on tracks, to 0.001 px on
    the residual, and 75 % in recurrence.
- **Before you use it.** The tracking settings page, when it saves, drops a tube project's line-detector, OTF and
  depth-cue settings (section 5). VSC's message therefore says to set the 1.0 px tolerance in config.json. A fix to
  the settings page needs your OK.

## 1. What was built

**The library (C++).** In `inc/libMath/Camera.h` and `src/srcMath/Camera.cpp`:

- **`ImageCorrection`:** a field c = (du, dv) on a grid of nodes, 8 px apart, read bilinearly between them.
  - **What it means:** a detection at pixel d has the camera model's image point d − c(d). This is the study's
    convention, so its fields carry over as they are.
  - **The file:** text: `VERSION 1`, `IMAGE_SIZE`, `GRID u0 v0 step nu nv`, then `DU` and `DV`.
  - **Checks:** the file must be well formed, its values finite, and its slope bound below 0.5. The bound guarantees
    that the projection's fixed point converges.
- **`CorrectedCamera`:** wraps any camera model.
  - **Projection:** it solves d ← q + c(d), with q the model's projection, to 1e-11 px.
  - **Line of sight:** the model's line of sight through d − c(d).
  - **Several images and hints:** `projectAll` and `projectWithHint` move every image. Hints stay the model's rays.
  - **`imageStatus`:** applies the curved port's rule to the moved images. That rule now sits in one helper,
    `statusOfImages`, which both cameras use.
  - **Which image is "the" image** stays the model's choice.
  - **Line images:** a pinhole or flat-window camera reports curved line images once corrected, since a shift that
    varies bends them.
  - **Unchanged:** the camera's type and other properties, and its file (`saveParameters` writes the model's file
    alone).
- **config.json:** `"cameras": [{"file": ..., "correction": "camFile_VSC/vsc_cam1_corr_p2.txt"}]`, with the path
  relative to config.json.
  - The tracking log says `Camera 0: image correction <file>`.
  - A missing file, a file of the wrong image size, a malformed file or one too steep stops the run, naming the file.
  - Text configs (config.txt) carry no correction.
- **The bubble-size code** reads focal lengths through the wrapper (`baseCamera`), so it works with a corrected
  camera too.
- **Python bindings:**
  - `lpt.ImageCorrection` (`load`, `fromGrid`, `at`, `toModel`, `toImage`);
  - `lpt.CorrectedCameraModel`;
  - `lpt.loadCameraModel(file, correction="")`;
  - `CameraModel.clone()`;
  - `lpt.Camera.setCorrection(path)` / `clearCorrection()` / `hasCorrection()` / `correctionFile()` /
    `cameraModel()`. The handle's parameter calls keep acting on the model.

**The GUI (Python).**

- **`modules/vsc/correction_io.py`:** the correction file in Python. It repeats the library's arithmetic operation
  for operation, so the two agree to the last bit (L1).
- **`modules/vsc/field_vsc.py`:** the study's estimator, at its chosen settings:
  - the points: every long-track point;
  - the detections: the run's own detector (T1's line detector with its noise), paired one to one within the radius
    you set (default r + 1 = 3 px);
  - the fit: projected least squares on 2–4 cameras, a 10 × 6 B-spline per camera and component, Cauchy weights, a
    noise model, and a bending weight chosen on held-out frames;
  - beyond the data, a smooth (harmonic) fill instead of the study's nearest-value fill, which had steps;
  - its work runs in 8 worker processes.
- **Passes:**
  - **The total:** a camera that already has a correction c1 gets the rest c2 fitted against its corrected model,
    and the total c2(d) + c1(d − c2(d)) is written as the next pass.
  - **Files:** earlier passes' files stay, and config.json is backed up once.
  - **The guard:** a pass refuses tracks older than the current correction ("rerun tracking with it first").
- **`VSCService.run`:** dispatches projects with PINCYL or PINSPH cameras to it. A tube project with only config.txt
  is refused, with the conversion to do.
- **The tracking view:**
  - a note under the VSC group (tube projects only);
  - the finish message: the pass, the residual before and after, the tolerance advice, and the next step;
  - the 2-D overlay's green marks: the projections through the corrected cameras;
  - a new "Correction" tab: |c| in colour, arrows, and the detections used, per camera.

## 3. T1, end to end

`compare_t1.py`, the study's measures. T1 has no truth, so:
- **Ghost share at frame 100,** two estimates:
  - **counts:** the control's active long tracks over the run's;
  - **swirl:** tracks that do not follow the flow.
- **Recurrence** against the study's warped two-pass run: the share of tracks with half their points within 0.1 mm of
  the other run's.
- **The residual no 3-D move explains** (with two cameras the offset across the epipolar curves), measured on every
  5th frame through each run's own cameras and frames.

## 5. Found along the way

1. **The tracking settings page drops a tube project's tracer settings when it saves.** (Fixed 9 Oct,
   `2026-10-09-report.md`.)
   - **What I checked** (`g3_settings.py`): a T1 project after a VSC pass, its 2-D tolerance set to 1.0 px, saved.
   - **What survives:** the cameras' corrections, and the tolerance does become 1.0 px.
   - **What is lost:** the page rebuilds the tracer from its form, so these go: `detector`, `lines`, `otf_file`,
     `roi_from_otf`, `roi_sigma`, `shape_check`, `shape_tol_px`, `shape_tol_rel`. The next run would use the spot
     detector without the OTF table or the depth cue.
   - **Not caused by this change:** it has applied to every tube project since the line detector came in.
   - **For now:** VSC's message says to set `objects[0].ipr.tol_2d_px` in config.json, and names what a Save would
     drop.
   - **The fix** would keep the loaded object's settings that the form does not show, as the page already does for
     the cameras. It needs your OK.
2. **`tests/stb_improve/build_variant.py` deletes your GUI's `build/Release/OpenLPT.exe` during every build.**
   - CMake writes the exe into the source tree, so the tool deletes it and then restores a saved copy. Today that copy
     equals your exe (same hash), but during the build the exe is missing.
   - I built from a copy of the source instead (`build_vcf.py`), so your exe was never touched (its hash checked
     before and after).
3. **A latent race in the tracking view's VSC finish handler, which the dialog hides.** (Fixed 9 Oct.)
   - The handler lets go of the worker's QThread right after its message box.
   - In the GUI the box is modal and runs its own event loop until you click OK, and the thread ends during it. A
     harness without that loop crashes (exit 127).
   - The same code serves today's VSC, so I left it. A `thread.wait()` before letting go would make it safe; it is
     yours to decide.
4. **The vendored oracle `test/refs/project_cylinder.py` no longer matches the notes repo's `code/project_cylinder.py`.**
   (Re-copied 9 Oct.)
   - It fails pytest with today's library too, so it is unrelated to this change.
   - Re-copying the file fixes it.

## 6. To use it

1. **Install** (with your OK): `python build_local.py` with the refract interpreter. That rebuilds the module the GUI
   loads (`build-py/Release/`) and `build/Release/OpenLPT.exe`.
   - An exe built before this change would only warn about the `"correction"` key and ignore it.
   - The VSC therefore refuses to run with a module that lacks `lpt.ImageCorrection`.
2. **Track** as usual, then press **Run VSC**.
   - On a tube project it writes the corrections and points config.json at them.
   - The Correction tab shows the fields, and the 2-D view shows red detections, yellow projections before and green
     projections after.
3. **Set the 2-D tolerance to 1.0 px in config.json** (`objects[0].ipr.tol_2d_px`; not through the settings page, see
   section 5). Then **track again and Run VSC again**: that is pass 2.
   - Stop when a pass changes the field little. On T1, pass 1 changed it by 0.30 / 0.40 px RMS and pass 2 by
     0.14 / 0.11 px.
4. **To undo it,** remove the cameras' `"correction"` keys, or restore `config_backup.json`.
