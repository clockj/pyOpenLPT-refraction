## 1. What changed

- **`gui/views/tracking_settings_view.py`.** It applies to projects with tube or sphere cameras (PINCYL, PINSPH), and
  only adds code.
  - **Save:** the object's settings that the form does not show are kept from the loaded config, at every level
    (`merge_unshown`). This applies when the form's object type equals the loaded one, and the form's values win.
  - **The view volume of a rig whose cameras are all tube or sphere cameras** comes from their rays
    (`_curved_port_common_box`).
    - **The rays:** each camera's lines of sight through a grid of pixels, the sensor's edges included. The grid is
      dense enough that neighbouring rays lie about 1 mm apart, up to 129 × 81. Each ray is cut to the stretch inside
      the port's inner surface.
    - **The region both base cameras see:** where the rays of the two most oblique cameras pass within one ray
      spacing of each other.
    - **Further cameras:** a point counts when one of their rays passes within one spacing. Points are tested from the
      outside in, until each side's outermost one is found.
    - **The box:** widened by one spacing, then rounded outward to 5 mm and given 1,000 voxels across x, as the page
      does for other rigs.
  - **Mixed rigs** (tube and plate cameras together) keep today's search. None exists to test.
- **`gui/views/tracking_view.py`:** `_release_vsc_thread()` stops (`quit`) and waits for (`wait`) the worker's
  thread, then lets go of the worker and the thread. The finish and error handlers call it.
- **`modules/vsc/field_vsc.py`:** the tolerance advice names the tracking settings.
- **`test/refs/project_cylinder.py`:** re-copied from `code/project_cylinder.py`.
- **`build-py/Release`, `build/Release/OpenLPT.exe`:** rebuilt by `build_local.py`.

**A deviation from the plan.** The plan said the volume estimate would project tube cameras through the library, as
it does for PINPLATE cameras. That was not enough:
- **The search itself fails on a long lens.** It starts from a box about 1.9 m deep, sampled 20–30 mm apart, so it
  never lands in T1's view, which is about 31 mm wide. This happens with either projection.
- **Projection is slow here.** A tube camera's projection without a hint costs about 0.2 ms per point, and the search
  samples up to 227,000 points per camera.

So tube rigs get the ray-based estimate instead. Today's search is unchanged for every other rig.

## 4. Follow-up 2 (afternoon): the GUI detects as the tracking run does

You asked:

> please fix the bugs on line detector, i want the gui behaves the same as the actual tracking code run without gui

**The reference is the tracking run itself.**
- **How it detects:** it loads each frame with ImageIO from the config's folder, then calls
  `ObjectFinder2D.findObject2D(frame, settings, camera index)`.
- **What it logs:** every frame, its detections per camera.
- **Where:** the first IPR pass of the initial frames (0–3) runs on the frame as loaded, so those lines are the run's
  detection.

**What was wrong:**
- **Validate** called the detector without the camera index. The line detector then estimated the noise from the
  frame instead of taking the camera's configured value.
  - **On 20261008:** 406 / 998 / 3,741 detections, against the run's 433 / 952 / 3,340 (−6 to +12 %).
  - **On T1:** 1,047 / 949, against 1,067 / 985.
- **The plate/pinhole VSC's crops** did the same. On a crop the estimate is far off: only 1–3 of 40 crops detected
  as with the configured noise.
- **The field VSC** gave the run's detections on these runs, but by a path of its own: OpenCV's frame, and the line
  settings rebuilt in Python. It would part from the run in three cases:
  - on 16-bit frames;
  - on a project without `lines.noise`, where it passed noise 0 and the run estimates the noise;
  - on image names relative to the config's folder.

**The fix:**
- **The binding:** `findObject2D` takes the camera's index (`cam_id`, default −1 as before).
- **Validate and the crops** pass it.
- **The field VSC** now makes the run's own call: ImageIO from the config's folder, the settings as the run reads them,
  and the index. With a module that lacks the index it refuses to run, naming the rebuild to do.
- **Rebuilt:**
  - the GUI's module (`build_local.py`): 985c59fd… → 3a35ba10…, no errors;
  - the exe: unchanged at 0784fae5…, since its sources did not change, so I1's tracking check still holds;
  - the test build vcf: from the current source.

**Tests (`d1_detection.py`, `queue_d1.sh`; S3 and G3 rerun).**

## 5. The double check: the flat-window calibration in the GUI

You asked:

> is the refract+plate calibration in gui updated the same as our new algorithm for that?

**It runs the same algorithm, but it cannot make the fit we delivered for the real case.** This is a read-only
comparison; I checked every point below in the code.

- **Same code.**
  - **The path:** the wand tab's Pinhole+Refraction runs `plate_wand.calibrate` in a separate process
    (`view._run_plate_wand_calibration` → `plate_wand_gui.child_run` → `run`).
  - **The files:** the same committed files the case scripts import; nothing in `modules/camera_calibration/` is
    uncommitted.
  - **The features:** the restarts, the window-normal hint paths, the weak-window scan, the warnings (in the message box,
    the results page and `calibration_report.txt`) and the library fixes of 3–4 Oct.
  - **Precalibrate** runs the same stages 1–3 (`start_candidates`).
  - **The old calibrator** runs only if its box is ticked.
- **What the GUI cannot set.** The real case's delivered fit, `calib_plate_wand_ref_centre`, was made with
  `--fit-k1 --channel --aim centre --start tests/states/t2_all.pkl`. Against that:
  1. **The start.** The case started from a verified fit (T2). The GUI can only search from scratch or "Refit from the
     last result" of the same session; it cannot load a saved fit or camFiles. The case's report (section 4): "From
     scratch on every frame, the calibration found a wrong minimum", which was not delivered.
  2. **Constraints.** The channel (100 / 150 mm, 3 mm tolerance) and the cameras' aim are held in the case. The GUI
     never passes `constraints` (`plate_wand_gui.run`: `calibrate(data, rig, start=, hints=, fit_k1=, n_final=,
     noise_weights=)`).
  3. **k1.** The GUI's distortion box starts at "None (0)", so k1 is fitted only if you pick "Radial k1". The case found
     k1 is needed.
  4. **Lens terms.** `fit_lens` (pp, k2, tangential) cannot be set, and the GUI refuses k1+k2. The pp-fitted variant
     (`calib_plate_wand_ref`) cannot be made in the GUI.
  5. **Hints.** The GUI never passes window-normal hints, so the hinted paths that rescued wrong minima on this rig are
     unreachable.
  6. **Windows.** One thickness and one set of indices apply to every window, defaulting to 10 mm. The case's walls are
     12.7 mm.
- **The same in both:** the wand length held, 5-sigma rejection, per-camera noise weights, the number of final fits
  (2, or 6 with "Thorough") and the start search.
- **A different calibrator:** the board-based "Plate Calibration" tab's own Pinhole+Refraction runs an older board
  calibrator (`RefractionPlateWorker`), not plate_wand.

**So:** for a rig like 20260727's, the GUI with its defaults would run the from-scratch configuration that went wrong
there. Adding the missing options to the wand tab would let it reproduce the delivered fit. Those are: start from a
saved fit or camFile folder, the channel and aim constraints, per-window thickness, and k1 for flat windows. That is a
GUI change, so it waits for your OK.
